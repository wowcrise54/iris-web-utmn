# Логирование IRIS v3

Backend, Celery, frontend SSR и браузер используют уровни `TRACE`, `DEBUG`,
`INFO`, `WARNING`, `ERROR`, `CRITICAL`. По умолчанию приложение пишет INFO,
сторонние библиотеки — WARNING. Технические события не заменяют аудит действий.

## Настройки при запуске

```dotenv
LOG_LEVEL=INFO
IRIS_LOG_FORMAT=json
IRIS_LOG_LEVELS={"iris.mcp":"DEBUG","iris.chatbot":"DEBUG","iris_maxpatrol_module":"INFO","iris_opencti_module":"TRACE","iris.frontend":"INFO"}
```

Для backend настройки доступны через существующий `.env.v3.live`. Для передачи
тех же значений в Compose-подстановки frontend используйте также
`--env-file .env.v3.live`. Не выводите этот файл или полный Compose config:
они содержат приватные настройки. Некорректные уровни и JSON блокируют запуск
с сообщением, которое не повторяет значение настройки.

Основные имена логгеров: `app` (существующий backend), `iris.api`,
`iris.worker`, `iris.mcp`, `iris.chatbot` (Yuki/LLM), `iris_maxpatrol_module`,
`iris_opencti_module`, `iris.frontend`, `iris.browser`. Переопределение Python
применяется к префиксу и его дочерним логгерам. Текстовый формат доступен через
`IRIS_LOG_FORMAT=text`; в Docker по умолчанию JSON, локально — текст.

Браузер по умолчанию использует INFO. Для локальной диагностики задайте
`localStorage.setItem('iris_log_level', 'DEBUG')` или `TRACE`; удаление ключа
возвращает INFO. Существующий переключатель `debug_api` также включает DEBUG.
Локальная настройка не меняет серверные уровни.

## Корреляция и содержимое

`X-Request-Id` содержит 1–128 символов `A–Z a–z 0–9 _ . : -`; некорректное
значение заменяется случайным ID. Proxy, frontend и backend сохраняют валидный
ID и возвращают его в ответе. Celery передаёт контекст в заголовке
`iris_log_context`; каждая задача получает собственный `task_id`.

Каждая запись содержит UTC-время, уровень, сервис, логгер, событие и сообщение.
При наличии добавляются request/task/user/customer/object IDs, этап, статус,
длительность и результат. User ID берётся из серверной авторизации. Для
браузерного события клиент не определяется из произвольного URL: это событие
пользователя без подтверждённого выбранного клиента.

Не передавайте тела, промпты, ответы LLM, вложения, исходные алёрты или IOC в
сообщения. Для новых вызовов используйте статический текст события и разрешённые
метаданные. Исключения выводятся как тип и позиции кадров без значений, исходных
строк и locals. Пароли, токены, cookies и URL credentials/query скрываются;
объекты, циклы, глубина и строки ограничены. Очистка — дополнительный барьер,
а не разрешение передавать произвольное содержимое в свободный текст.

OpenCTI TRACE выводит только размер, статус и длительность. Старый флаг
`IRIS_OPENCTI_LOG_PAYLOADS` больше не разрешает вывод тел. Результаты и аргументы
Celery не выводятся штатным `celery.app.trace`; жизненный цикл пишет
`iris.worker`. SQL и bound parameters из `sqlalchemy.engine` не выводятся
даже при DEBUG. Ручные bug reports сохраняют выбранные пользователем поля
в очищенных и ограниченных метаданных; автоматического дампа request body нет.
При создании новой пустой БД задавайте `IRIS_ADM_PASSWORD`:
сгенерированные пароли больше не печатаются в технических логах.

## Браузерные события

`POST /api/v2/observability/client-events` принимает `{"events":[...]}` через
существующие авторизацию и CSRF. Разрешённые поля события: `level`, `event`,
`message`, `request_id`, `path`, `stack`; уровни — WARNING/ERROR/CRITICAL.
Пакет: 1–20 событий, до 64 КиБ. Лимит: 60 событий в минуту на пользователя
в одном процессе backend; в текущем запуске Uvicorn один процесс. При
масштабировании на несколько процессов это не общий кластерный лимит.

Очередь браузера ограничена 60 событиями; отправка — пакетами раз в 5 секунд
с сетевым таймаутом 5 секунд. Ошибочные пакеты отбрасываются без повторов и
рекурсивных логов. Неавторизованные события не ставятся в очередь; события
предыдущего входа отбрасываются после выхода или смены пользователя. Backend помечает
записи `source=browser`; Sentry не получает их повторно через logging integration.
Обычные обработчики исключений Sentry остаются подключёнными.

## Docker и обновление

### Ошибки custom/OpenAI-провайдера

`llm_input` содержит размер сериализованного запроса в байтах (`request_bytes`),
число сообщений и инструментов. Текст запросов и заголовки не записываются.
Байты не являются точным числом токенов: для сравнения с окном, например 262k,
нужен токенизатор модели либо usage/диагностика самого провайдера.

При HTTP-отказе адаптер читает не более 16 КиБ тела ошибки. `llm_http_error`
указывает HTTP-статус, категорию и сколько байтов прочитано. Явная ошибка
`context_length_exceeded` или соответствующее сообщение провайдера показывается
пользователю как превышение контекста; HTTP 413 отдельно обозначает ограничение
размера запроса. Произвольный HTTP 400 не считается доказательством переполнения.

Для временной диагностики можно включить в окружении app/worker
`IRIS_CHATBOT_LOG_PROVIDER_ERRORS=1` и уровень TRACE для `iris.chatbot.openai`
через существующий `IRIS_LOG_LEVELS`. Тогда `llm_error_detail` содержит до 2048
символов тела ошибки после удаления активного API-ключа и общей очистки секретов
и URL. Заголовки не логируются. TRACE может содержать операционные данные,
которые провайдер повторил в ошибке; включайте временно и отключайте после проверки.

Для standalone эти переменные передаются в app/worker из `.env` через Compose:

```dotenv
IRIS_CHATBOT_LOG_PROVIDER_ERRORS=1
IRIS_LOG_LEVELS={"iris.chatbot.openai":"TRACE"}
```

Если `IRIS_LOG_LEVELS` уже настроен, добавьте ключ в существующий JSON, сохранив
остальные уровни. После изменения окружения нужны пересоздание app/worker и
пересборка их общего backend-образа с исправленным адаптером. После диагностики
верните `IRIS_CHATBOT_LOG_PROVIDER_ERRORS=0` и прежние уровни.

`stream_output_bytes` (и прежнее поле `response_bytes`) измеряет только полученный
вывод модели, а не HTTP-тело ошибки. Значение 0 не означает пустую ошибку.
Событие `llm_completed` теперь требует `MessageEnd`; при отказе записывается
`llm_failed`. В прежнем коде `llm_completed` возникало и после ошибки.

Новые ограничения истории, выборка событий и молчаливое удаление tool results
этим исправлением не вводятся. Существующий `max_tool_calls_per_turn` сохраняется:
0 отключает лимит итераций. Полное чтение больших исходных событий по-прежнему
может не помещаться в окно конкретной модели или лимит API-посредника.

Для app, worker, frontend и nginx включён `json-file`, `max-size=20m`,
`max-file=5`. Это лимит объёма на контейнер, а не срок хранения. Nginx пишет
JSON access logs без query, Referer, cookies и заголовков. Ошибки HTTP отражаются
в этом потоке с ERROR/WARNING, upstream status и временем. Штатный runtime error
log Nginx отключён, поскольку он включает исходную строку запроса с query;
диагностика запуска и проверки конфигурации остаётся доступна через stderr.

Все команды выполняются из корня репозитория с закреплёнными параметрами:

```powershell
$irisCompose = @('-p', 'iris-upgrade-2-4-29-fastapi',
  '-f', 'docker-compose.upgrade-validation.yml',
  '-f', 'docker-compose.saved-data.yml',
  '-f', 'docker-compose.v3.yml', '-f', 'docker-compose.v3-live.yml')
docker compose @irisCompose logs --since 10m app worker frontend nginx
```

Перед пересозданием — проверка labels/томов, контрольных записей и резервная
копия обеих БД и файлов по `AGENTS.md`. Обновляйте app и worker совместно;
db/rabbitmq и тома не пересоздавайте. Для отката используйте сохранённые образы
и прежнюю конфигурацию логирования, без восстановления БД поверх новых данных.
