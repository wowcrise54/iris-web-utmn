# MP10 28.0: события инцидента и вложенные события

Проверено 21 октября 2026 года по официальной русской справке
**MaxPatrol 10 28.0**, открытой в браузере. Поисковая выдача преимущественно
содержала справку 26.2; приведённые ниже ссылки относятся именно к 28.0.
Это исследование контракта, а не подтверждение запросов на рабочем SIEM.

## Подтверждённые методы

### Список событий с нормализованными полями

`POST /api/events/v2/events`

[Получение списка событий](https://help.ptsecurity.com/ru-RU/projects/mp10/28.0/help/10836123659)

- Query `incidentId` задаёт UUID инцидента, с которым связаны события.
- Query `limit`, `offset` задают постраничную выборку.
- Query `recursive` относится **к вложенным группам активов**, не к дочерним событиям.
- Body `filter.select` задаёт выбираемые поля, `filter.where` — предикат фильтра.
- Body `timeFrom` обязателен, время задаётся в Unix-формате; `timeTo` необязателен.
- Есть параметры `filter.searchType`, `searchSources`, `localSources` для распределённого поиска.
- Ответ содержит `events`, `totalCount`, `token`. Токен представления можно
  передавать в последующих запросах; текущий модуль его не использует.
- В примере обычного события `id` — имя типа/правила нормализации;
  уникальный идентификатор экземпляра — `uuid` и `_meta.id`.
  Нельзя дедуплицировать экземпляры по полю `id` нормализованного объекта.

### Ссылки на события инцидента

`GET /api/incidents/{incidentId}/events`

[Получение событий по инциденту](https://help.ptsecurity.com/ru-RU/projects/mp10/28.0/help/7408309387)

- Query `limit`, `offset`.
- В ответе описаны `id` (UUID из поля `uuid`), `date` (из `time`),
  `description` (из `text`). Пример ответа — массив, а не объект с `events`.
- Это список ссылок/кратких описаний, не весь набор нормализованных полей.
- В справке есть противоречие: метод в описании — GET, а в примере — POST.
  Метод требует проверки по OpenAPI или фактическому ответу установки 28.0.
- Справка предупреждает об ограничениях выгрузки большого числа событий
  в Elasticsearch и LogSpace.

### Read model

`GET /api/incidentsReadModel/v2/incidents/{incidentId}/events`

[Получение данных о событии](https://help.ptsecurity.com/ru-RU/projects/mp10/28.0/help/4589536907)

Публичная страница описывает только `id` и `timestamp`; несмотря на название,
она не подтверждает получение полного события или дерева вложенных событий.
Нельзя считать этот метод API полного raw-содержимого без дополнительной проверки.

## Подтверждённые поля и связи

[Схема полей событий](https://help.ptsecurity.com/ru-RU/projects/mp10/28.0/help/2203906443)

| Поле | Смысл |
|---|---|
| `uuid` | UUID экземпляра события; у исходного и нормализованного вида совпадает |
| `body` | Текст необработанного события UTF-8 |
| `mime` | Формат исходного события: текст, JSON, XML, Windows eventlog и др. |
| `normalized` | `true`: нормализованное или корреляционное; `false`: необработанное |
| `subevents` | UUID событий, породивших агрегированное или корреляционное событие |
| `subevents.time` | Времена регистрации событий-оснований |
| `subevents.missed` | UUID событий-оснований, недоступных при обработке корреляции |
| `count.subevents` | Количество событий-оснований |

Вложенность здесь — связи между событиями, а не повторная нормализация в IRIS.
Нормализацию уже выполняет MP10; IRIS должен сохранять полученные поля и оригинал.
Общий процесс описан в [этапах обработки событий](https://help.ptsecurity.com/ru-RU/projects/mp10/28.0/help/734890251).

## Что найдено в текущем модуле

- Связанные события уже сохраняются в `alert_source_content.events`.
- Выборка включает `uuid`, `body`, `mime`, `subevents`, `subevents.missed`,
  но не включает `subevents.time` и `normalized`.
- UUID из `subevents` отдельно не раскрываются — полного дерева сейчас нет.
- Для событий применяется то же скользящее окно, что для поиска инцидентов.
  Оно может исключать старые события-основания, связанные с новым инцидентом.
- Уже импортированные инциденты полностью пропускаются; добавленные позже
  связанные события и неуспешно полученные ранее события не дополняются.
- UI сырого события читает `alert_source_content`; изменение этой структуры
  позволит показать полученные материалы в существующем JSON-представлении.

## Предлагаемый объём следующей доработки

1. Сохранить существующие `incident` и `events`, расширив выбираемые служебные поля.
2. Получать события-основания по UUID из `subevents`, обходя вложенные связи
   и исключая циклы/повторную загрузку UUID. Идентичность исходного и
   нормализованного вида одного UUID учитывать отдельно.
3. Сохранять нормализованные поля без переименования, исходные `body`/`mime`
   при их наличии и вложенную структуру связей для последующего анализа.
4. Не ограничивать события-основания окном создания инцидента: учитывать
   их собственные временные метки. Проверить извлечение raw- и normalized-вида
   на обезличенном ответе или тестовой установке 28.0.
5. Явно сохранять неполноту: недоступные UUID, ошибки получения, ограничения
   хранилища и прерванный обход. Не подменять неполную выборку утверждением «все события».
6. Дополнять связанные материалы уже созданных оповещений без создания дублей
   и без замены пользовательских названия, описания, статуса или заметок.

Отдельный документированный параметр рекурсивной загрузки дерева событий
в изученных разделах API не найден. Непроверенные UI-endpoints не использовались.

## Уточнение при реализации раскрытия subevents

В первичном коде [EventsAPI SDK](https://github.com/GenRockeR/mpsiemlib/blob/main/mpsiemlib/modules/EventsAPI.py)
найдены методы полного нормализованного события и связанных событий:
`GET /api/events/v2/events/{uuid}/normalized?time=…` и
`POST /api/events/v2/subevents/{uuid}?field=subevents&time=…&limit=…&offset=…`.
Автор описывает проверку на R28.0 и обёртку `event.Data` для полного события.
Эти методы использованы в доработке с автономными тестами обоих форматов;
на установке пользователя запросы не выполнялись. SDK не добавлялся в зависимости,
исходный код его методов в модуль не копировался.

Автор также указывает, что старый `/events/{uuid}/raw` не маршрутизируется в R28.0.
Поэтому сохраняется `body`, полученный в ответах SIEM, без обещания выгрузить
необработанный оригинал отдельным API во всех случаях.

## Уточнение по фактическому ответу установки пользователя

Пользователь предоставил запрос `POST /api/events/v3/events/` с `incidentId`,
`offset`, `limit=250`, `noCount=true` и строковым PDQL в поле `filter`.
Ответ содержит `errors`, `events`, `totalCount`, `token`.
В предоставленной выборке 12 событий: одно содержит 11 UUID в `subevents`,
и все эти UUID присутствуют среди остальных строк. У 11 событий есть исходный
`body`; `_meta`, `_checkpoint`, `_presentation` и `_whitelisting` также доступны.
`count.subevents` имеет `null`, поэтому сам по себе этот счётчик не подтверждает
отсутствие дочерних событий.

Модуль переведён на этот v3-запрос с передачей токена между страницами.
Ответ считается достаточным для построения дерева, если все дочерние UUID
присутствуют; дополнительные UI-запросы выполняются только для отсутствующих
дочерних событий. `null` и пустые контейнеры сохраняются. Локальный прогон
на предоставленном ответе подтвердил сохранность всех объектов и одного дерева
с 11 дочерними событиями без дополнительных HTTP-запросов. Доступ к рабочему SIEM
не выполнялся; исходные приватные события не копировались в репозиторий.
