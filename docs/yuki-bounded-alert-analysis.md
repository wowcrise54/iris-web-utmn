# Полный фоновый анализ оповещений

Кнопка «Анализировать в Yuki» создаёт задание и отдельный диалог, привязанный к
оповещению и его клиентской политике. История чата содержит запрос аналитика и
готовый отчёт, а не страницы исходных событий. Переключение/закрытие панели не
останавливает worker. Задание можно открыть из истории оповещения либо по
`/alerts/<id>?analysis=<job_id>`.

## Обработка и полнота

Worker фиксирует JSON-снимок полей оповещения, IOC и активов, его SHA-256 и время.
Включаются названия, типы, описания, теги и уже сохранённое обогащение; новых
внешних проверок при подготовке снимка не выполняется.
На диске сохраняется исходное значение, включая исходную строку JSON, если БД
хранит строку. Для анализа такая строка дополнительно разбирается как JSON.
Типизированный граф ссылок выделяет только точные повторы; неизвестные поля,
варианты одного UUID, связи и число вхождений сохраняются. Манифест позволяет
восстановить нормализуемое значение без потерь. Команды из событий не выполняются.

Каждый пакет проходит отдельный запрос без инструментов. Факты сохраняются в
структурированном виде со ссылками на источники. Последующие уровни объединяют
ограниченные заметки; выводы перепроверяются по исходным фрагментам. Не получившие
подтверждения утверждения исключаются из вердикта и учитываются как ограничение.
Отчёт строится из проверенных фактов, а не произвольного итогового текста модели.

Покрытие относится ко всем доступным пакетам снимка. Оно **не подтверждает**
полноту исходного сбора. Например, 9 обработанных событий и 6 отсутствующих
связанных событий дают итог `partial`, даже если обработка закончилась.
Для новых/дополученных событий запускайте «Анализировать актуальное оповещение».
Кнопка продолжения после сбоя использует прежний неизменяемый снимок.

## Бюджет и LiteLLM

В глобальных настройках Yuki и в клиентской политике добавлено поле контекстного
окна. `0` означает неизвестное/автоматическое значение. Для текущей Qwen задайте
`262144` **после сверки фактического max context сервера за LiteLLM**. Прокси не
увеличивает окно, с которым был запущен inference backend.

Рабочий вход пакетного анализа ограничен 32768 токенами. Учитываются системный
промпт, сообщения и схемы инструментов; резервируются ответ и 10% физического
контекста. Стадии используют до 8192 выходных токенов, либо меньший заданный
пользователем положительный лимит. Обычные настройки `0 = без ограничения` не
переопределяются для обычного чата/Sandbox; пакетный анализ имеет собственную
ограниченную рабочую память.

IRIS обращается к `/utils/token_counter` только на настроенном адресе провайдера,
с текущими credentials, без редиректов и с таймаутом 2 секунды. Поддерживаются
ответы LiteLLM с `count_source=provider`. Для локальной оценки Hugging Face
требуется проверенное оператором соответствие alias и возвращённого `model_used`:

```dotenv
IRIS_CHATBOT_TOKENIZER_MODELS={"qwen3.8-fast":"<фактический model_used>"}
```

Перед включением сопоставьте `model_used` и `huggingface_tokenizer` с конфигурацией
фактической Qwen. Не подтверждайте OpenAI/tiktoken fallback для Qwen. Локальная
оценка остаётся оценкой, а не точным числом оплаченных токенов. Без подтверждённого
счётчика полный сериализованный запрос пакета ограничивается 16 КиБ.

Обычный чат использует отдельную проверку: каталог MCP сам может превышать 16 КиБ.
При неизвестных окне и токенизаторе действует явно обозначенный защитный предел
1 МиБ на полный запрос; при заданном окне применяется консервативная байтовая
граница с резервом ответа. Это не утверждение, что любое сообщение помещается в
реальную модель. История не удаляется и не обрезается молча: при превышении
предлагается отдельный фоновый анализ.

## Продолжение, кеш и безопасность

После каждого шага сохраняется контрольная точка. Явный отказ по размеру текущего
пакета приводит к его уменьшению, максимум с двумя повторениями после отказа
провайдера. Ошибка сети/структуры/лимита ответа не помечает пакет обработанным.
Отмена завершается после текущего запроса. Блокировки PostgreSQL предотвращают
перезапись отмены контрольной точкой и обеспечивают один запрос анализа к одному
развёртыванию модели; остальные задания ожидают.

Снимки изолированы по пользователю, клиенту, содержимому, модели, версии обработки,
настройкам и политике. Неизменившиеся пакеты могут повторно использовать результат
между разными снимками в пределах той же пользовательской/клиентской области.
Версионируйте alias модели при смене весов/токенизатора за LiteLLM.
Смена клиента или назначенной политики закрывает доступ
к старому диалогу/снимку; нужно новое задание. Подтверждённые результаты одного
снимка повторно используются без новых запросов к модели. Обновление самого
оповещения не меняет старый снимок, но в отчёте появляется предупреждение.

Файлы находятся в каталоге `alert-analysis` рядом с datastore, внутри `server_data`.
Права новых файлов — 0600, каталогов — 0700; ссылки и хеши проверяются. Снимки
автоматически не удаляются. Лимит одного workspace — 512 МиБ, при нехватке места
задание останавливается явно. Учитывайте каталог в резервных копиях и мониторинге
свободного места; его содержимое — операционные данные, а не обычные логи.

## Проверки и внедрение

Офлайн-проверка на конкретном JSON без отправки данных в LLM:

```powershell
python v3/backend/scripts/benchmark_alert_source.py 'C:\путь\message.txt'
```

Она выводит размеры, сохранность, покрытие и время нормализации. Это не измерение
токенов или времени inference. Для них сравнивайте реальные `llm_input`, аудит
egress и время одного и того же оповещения: холодный запуск и повторный запуск.
Не публикуйте исходные события и TRACE-полезную нагрузку в общих логах.

Обновление требует миграции `utmn_alert_analysis01` и пересборки backend/worker и
frontend. До изменения рабочей БД выполните проверки labels, проекта, томов,
контрольных записей и резервных копий по `AGENTS.md`. Для удалённого standalone
используйте его **фактическое существующее** имя проекта и Compose-файлы.
Не запускайте standalone поверх локального четырёхфайлового v3-стека.

Порядок обновления: сохранить все БД и файловые тома; собрать `app` и `frontend`;
обновить `app` и дождаться healthy после миграции; затем пересоздать `worker` и
`frontend` с теми же данными. Сначала проверьте одно оповещение: покрытие, живые
запросы, отмену/продолжение, повторный запуск без LLM и историю. Лишь затем
переходите к штатному использованию. Старые Sandbox/PCAP-задания сохраняются.
Downgrade с alert-scoped данными намеренно отклоняется, чтобы не потерять область
доступа; простой откат версии контейнера не заменяет план отката данных.

### Команды для существующего standalone на Linux

Сначала перенесите изменения в существующий checkout сервера. Из его каталога
проверьте базовый commit по `bounded-alert-analysis-patch-info.txt`, если используете
переданный patch-файл. Для этой поставки он указан в сопроводительном файле.

```bash
git status --short
git rev-parse HEAD
git apply --check /tmp/bounded-alert-analysis.patch
git apply /tmp/bounded-alert-analysis.patch
```

При отличающейся базе/конфликтах не применяйте patch принудительно: сначала
согласуйте изменения с вашей версией. Если исходники подключены к работающим
контейнерам bind-mount, остановите app/worker до переноса файлов. Стандартный
standalone использует исходники внутри образа, без такого bind-mount.

Из каталога проекта
проверьте `docker ps --format 'table {{.Names}}\t{{.Ports}}'`, затем labels nginx:

```bash
docker inspect ИМЯ_NGINX --format '{{index .Config.Labels "com.docker.compose.project"}} {{index .Config.Labels "com.docker.compose.project.config_files"}}'
```

Имя проекта ниже возьмите **из labels**, а не из имени новой папки. Если в labels
есть дополнительные Compose-файлы, сохраните их в функции `dc`. Эти команды
предполагают стандартные пути файлов и пользователя PostgreSQL `postgres`.

```bash
set -e
PROJECT='ИМЯ_СУЩЕСТВУЮЩЕГО_ПРОЕКТА'
dc() { docker compose -p "$PROJECT" -f docker-compose.standalone.yml "$@"; }
dc ps
docker inspect "$(dc ps -q db)" --format '{{json .Mounts}}'

# Сверьте прежние кейсы/алёрт в интерфейсе до обновления.
# Сборка выполняется, пока старые контейнеры ещё работают.
dc build app frontend
umask 077
mkdir -p "$HOME/iris-backups"
BACKUP_DIR="$HOME/iris-backups/before-bounded-analysis-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -m 700 "$BACKUP_DIR"

# Короткое окно обслуживания; db/rabbitmq и nginx остаются запущенными.
dc stop worker app
dc exec -T db pg_dumpall -U postgres > "$BACKUP_DIR/postgres.sql"
test -s "$BACKUP_DIR/postgres.sql"
grep -q 'PostgreSQL database cluster dump complete' "$BACKUP_DIR/postgres.sql"
dc cp app:/runtime "$BACKUP_DIR/runtime"
dc cp app:/home/iris/server_data "$BACKUP_DIR/server_data"
dc cp app:/home/iris/downloads "$BACKUP_DIR/downloads"
dc cp app:/home/iris/user_templates "$BACKUP_DIR/user_templates"

# Общий backend-образ используется app и worker. Сначала миграция и healthy app.
dc up -d --no-deps --no-build --pull never --force-recreate --wait --wait-timeout 300 app
dc up -d --no-deps --no-build --pull never --force-recreate worker frontend
dc ps
```

Если любая команда завершилась ошибкой, дальнейшие команды не выполняйте до её
разбора. Резервная копия `runtime` содержит конфиденциальную конфигурацию; не
выводите её содержимое. Исходные тома и имя Compose-проекта сохраняются.

После запуска откройте настройки Yuki, укажите фактические `262144` в глобальных
настройках либо назначенной клиентской политике. Начните с одного оповещения и
проверьте отчёт, исходники, повторное открытие истории, отмену и продолжение.
Для снимка из приложенного примера ожидается **9 доступных / 6 недостающих**;
при обновлённом источнике числа могут измениться. Затем повторите запуск без
изменения снимка: `stats.model_requests` должен быть 0, результаты берутся из кеша.
Сверьте наличие прежних контрольных кейсов и алёртов после обновления.

Новые API: `POST/GET /api/v2/alerts/{id}/analysis`, `GET /{job_id}`,
`POST /{job_id}/retry`, `POST /{job_id}/cancel`, `GET /{job_id}/sources/{source_id}`.
Каждая операция повторно проверяет владельца и доступ к исходному клиенту.
Инструменты в новом alert-scoped диалоге ограничены чтением своего оповещения и
его анализом; ID подставляется сервером, в том числе после ручного подтверждения.
Для анализа других оповещений/кейсов используйте отдельный диалог.
MCP `iris_alerts_analyze_start` и `iris_alerts_analysis_get` возвращают только
ограниченные метаданные/ссылку; отчёт остаётся в связанном диалоге.
