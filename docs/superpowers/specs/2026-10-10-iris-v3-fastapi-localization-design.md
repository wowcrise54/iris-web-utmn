# Переход IRIS на v3 с FastAPI и русской локализацией

Статус: подготовленный проект решения для согласования; реализация и переключение не выполнены.
Дата: 10 октября 2026 года.

## Цель и версия

Перенести действующее приложение с сохранением данных на официальный тег
`v3.0.0-beta.6`, адаптировать backend к native FastAPI/Uvicorn и перенести
английскую/русскую локализацию в новый SvelteKit frontend.
Стабильного тега `v3.0.0` в проверенном списке тегов нет. Версия фиксируется
по точным коммитам, а не по обновляемым веткам:

- iris-web: `cc172b492a271114b4ff4340abe273ee072f306f`;
- iris-backend: `77ec7a3a6932e970fdf18632d66d962c97e388be`;
- iris-frontend: `d1a6aa38b3b4fda5a7fb0d9ccf981e0a91c29f5d`.

Официальная beta не рекомендуется разработчиками для production.

## Подходы

Рекомендуется использовать точные исходники v3 и адаптировать существующий
native ASGI слой к её контрактам. Так сохраняются новые функции и бизнес-логика
upstream, а прежние адаптеры повторно используются там, где их контракты совпадают.

Полное переписывание всех обработчиков v3 на новый стиль FastAPI потребовало бы
более широких изменений бизнес-кода и усложнило бы проверку совместимости.
Поэтому оно не включено в этот переход. Требование native FastAPI означает,
что приложение Flask и WSGI-сервер не являются промежуточным рабочим backend.

## Backend

FastAPI владеет HTTP-маршрутизацией и ASGI-протоколом; Uvicorn запускает сервер.
Повторно использовать проверенные части `app.web`, `extensions`, форм и контекстов,
адаптируя их к v3. SQLAlchemy, транзакции, бизнес-проверки и схема v3 сохраняются.

Зафиксировать контракты из неизменного upstream v3: маршруты, методы, статусы,
JSON, cookies, OpenAPI, авторизация API-ключами/JWT, MFA, refresh/revoke,
OIDC и права доступа. Не переносить старую авторизацию поверх новой.
Изменять инфраструктурные импорты и запуск; различия бизнес-кода отдельно объяснять
и проверять. Сохранить лимиты загрузок, CORS/CSRF и экранирование.

Socket.IO адаптировать к native ASGI с учётом новых namespaces, аутентификации,
входа/выхода из комнат, отключений и worker-событий. Для Yjs сохранить
серверное состояние документа, ACL на каждом действии и ограничения сообщений.
Проверить настройки брокера событий v3; текущий in-process transport не считать
автоматически достаточным для межпроцессных уведомлений.
Сохранить HTTP-контракт MCP и проверку прав. API-интеграции перевести на
поддерживаемые внешние маршруты v3; legacy пути не объявлять совместимыми без теста.

## Локализация

Сохранить английский язык по умолчанию, переключение EN/RU, запоминание выбора,
русские формы множественного числа и fallback к английскому.
Переиспользовать переводы существующего `.po` каталога после проверки контекста;
новые тексты переводить отдельно. Перенести явные вызовы переводчика в Svelte
компоненты, сообщения действий, диалоги, таблицы, графики, редакторы и доступные
подписи. Пользовательские данные и идентификаторы API не переводить.

Локаль SSR должна быть изолирована для каждого запроса и совпадать при hydration;
общая изменяемая глобальная локаль на сервере недопустима. Выбор передавать
между frontend и backend безопасно и проверять по allowlist. По возможности
сохранить действующий выбор из подписанной cookie; формат сменить только с
описанной совместимостью. Не добавлять колонку БД исключительно для этой задачи.

Покрыть существующие разделы и новые war rooms, кластеры, сценарии расследования,
уведомления, почту и API-документацию интерфейса. Проверять инвентарь видимых
строк, а не только наличие словаря. Полное отсутствие английского текста в
пользовательских данных, логах или сообщениях сторонних модулей не обещается.

## База данных и развёртывание

Создать изолированный стенд на отдельных копиях БД и файлов; основной проект
и исходные тома сохраняются. PostgreSQL 18 получает новый явно именованный
external-том; каталог PG12 к PG18 не подключать.

Восстановить логическую копию БД, затем выполнить проверенный переход схемы v3.
Текущей revision `e5d79b8c4a55` нет в исходниках beta.6; у v3 другая миграция
дашбордов `c7f1e2a4d810`. До миграции построить обе цепочки и сравнить фактическую
схему. Подготовить совместимый переход с сохранением записей и расширением
существующих таблиц. Не использовать слепой `alembic stamp head` и не пропускать
миграции ради запуска. Проверить повторный запуск и сохранение установленной revision.

Добавить сборку frontend и маршрутизацию nginx из точного тега v3.
Для финального запуска сохранить проект `iris-upgrade-2-4-29-fastapi`, оба
закреплённых Compose-файла и добавить явный v3 override; все команды запускать
из корня репозитория с полным набором `-p` и `-f`.
Сохранить публичный адрес 18543. Все источники и готовые образы v2 сохранить
для восстановления; изменённые метаданные развёртывания документировать.

## Проверка до переключения

1. Проверить запуск backend/worker/frontend/nginx и готовность брокера.
2. Выполнить upstream unit/API проверки и контрактные тесты native FastAPI;
   сравнить поведение авторизации, MFA, refresh/revoke, ACL и MCP с upstream.
3. Проверить два одновременных клиента: чат, уведомления, Yjs-редактирование,
   сохранение после отключения/перезапуска и недоступность чужих документов.
4. Выполнить frontend typecheck, сборку, тесты локализации и браузерные сценарии
   в EN/RU: вход, MFA, кейс №2, алёрт №1 и новые разделы. Проверить подписи,
   клавиатуру, адаптивность, SSR/hydration и сохранение выбора языка.
5. Сравнить ID/UUID, связи и содержимое кейсов/алёртов и связанных объектов,
   пользователей/прав, дашбордов, а также файлы по манифесту и хешам.
   Сравнение учитывать преобразования модели v3, не только количество таблиц.
6. Проверить восстановление v2 из подготовленных копий на отдельном стенде.

Тесты не ослаблять для получения успешного результата. Сбой окружения или
непройденный обязательный контракт препятствует переключению рабочего приложения.

## Переключение и откат

Перед финальным снимком закрыть внешний доступ на запись, завершить запросы и
Socket.IO-сессии, остановить app/worker и другие производители/планировщики записи
выбранного стека. Создать новые резервные копии БД и всех файловых томов под одним
идентификатором, проверить копирование. Исходную PG12 базу сохранить неизменной.

Восстановить финальный снимок на PG18, применить проверенные миграции, подключить
v3 на прежнем адресе. До открытия доступа выполнить короткие проверки сохранённых
данных и сервисов; тестовые изменения выполнять на стенде, а не в финальной БД.
Если проверки не пройдены, вернуть конфигурацию и сохранённые образы v2,
подключённые к исходным томам, затем проверить те же записи.

После открытия записи v3 простой возврат к PG12 не сохраняет новые изменения.
При сбое сначала закрыть запись, сохранить PG18 и файловые изменения и определить
восстановление; не запускать v2 поверх старого состояния как будто откат без потерь.
Проверенный откат до открытия записи и это ограничение явно включить в инструкцию.
Старые тома и резервные копии не удалять.

## Результат работы

Исходники v3 с native FastAPI и EN/RU, воспроизводимая сборка и проверки,
сохранённые кейсы/алёрты/файлы, обновлённый стек на прежнем адресе,
инструкция миграции/отката и краткий отчёт с точными результатами проверок.
Данный документ фиксирует план; ни одно испытание v3 ещё не выполнено.
