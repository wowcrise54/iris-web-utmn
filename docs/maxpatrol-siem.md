# MaxPatrol SIEM → оповещения IRIS v3

## Упрощение сбора: очистка JSON при получении

Текущий маркер worker: `mp10-inline-clean-json-3`. После HTTP-ответа JSON
декодируется с удалением полей объектов, чьё значение равно null. Это происходит
до накопления событий, построения вложенности и сохранения в БД. Очистка
применяется ко всем вложенным объектам, в том числе внутри массивов. False, 0,
пустые строки и позиции массивов сохраняются; строковое содержимое body не меняется.

Изменения двух предыдущих коммитов (`d40466ed`, `ca245354`) отменены в исходниках:
удалены отдельное хранилище событий из рабочего кода, курсоры/бюджеты опроса
и постраничный просмотр. Полные очищенные события снова сохраняются в сыром JSON
алёрта с прежними events/event_tree. История Git не переписывается.

Для установок, уже применивших `utmn_maxpatrol02`, сохранён файл этой миграции
и добавлена совместимая `utmn_maxpatrol03`. Она возвращает сохранённые отдельно
небольшие наборы событий в алёрты внутри PostgreSQL и убирает устаревшие параметры лимитов,
не меняя токен и прочие настройки. Прежние таблицы оставляются как резервная
копия данных; сборщик их больше не читает и не заполняет. Downgrade/удаление
таблиц вручную не требуются. Перед применением — резервная копия по AGENTS.md.
На время миграции остановить прежний worker, чтобы он не записывал новые
манифесты параллельно переносу; после обновления запустить worker с новым кодом.
На свежей установке применяется та же непрерывная цепочка миграций.

Перед обратным переносом миграция сохраняет исходные MaxPatrol JSON больше 8 МиБ
целиком в `maxpatrol_payload_archive.payload` типа `json`, без преобразования
в JSONB и без загрузки документа в Python. В алёрте остаются компактные
`payload_archive_id`, `payload_bytes`, `archived_only=true` и `refresh_blocked=true`.
Это покрывает в том числе прежние inline-документы без event_storage и документы
226–418 МиБ, которые сами не помещаются в контейнер JSONB. Исходные значения
проверены по размеру и MD5 в PostgreSQL; они не удаляются и не очищаются при
архивировании. В таблице намеренно нет каскадного удаления вместе с алёртом.

Оставшиеся небольшие источники отбираются в MATERIALIZED CTE по размеру;
преобразования в JSONB выполняются только над этим ограниченным набором.
Обратный перенос затем измеряет объём отдельных событий. При общем размере
событий и текущего источника до 8 МиБ события возвращаются в алёрт. Более крупный
архив остаётся целиком в `maxpatrol_event_record`; в алёрте сохраняются счётчик,
размер, `event_storage.archived_only=true`, `event_collection.refresh_blocked=true`
и причина `legacy_payload_too_large`. Полный архив в этом случае не отображается
в сыром JSON алёрта. Worker пропускает его повторную загрузку; остальные инциденты
обрабатываются обычным порядком. Порог применяется при обратном переносе ранее
архивированных данных. Записи архива не удаляются.

Это исправляет сбой запуска `total size of jsonb object elements exceeds ...
268435455 bytes` в `utmn_maxpatrol03`, за которым frontend пишет ECONNREFUSED
при обращении к незапущенному backend. После обновления app неудавшаяся миграция
повторяется штатно. Исправление проверено на PostgreSQL 18.6, включая архив
больше 256 МиБ. Тестовые таблицы изолированы от рабочих данных.

Очистка уменьшает число полей и объём хранения, но не ограничивает размер
HTTP-ответа или число событий инцидента. Она не гарантирует устранение OOM
на крупных инцидентах; прежнее дублирование payload в event_tree возвращено.
Для проверки переноса есть тесты на PostgreSQL с временными таблицами:
`test_maxpatrol_inline_postgresql.py` (MAXPATROL_TEST_POSTGRES_URL).

Дальнейшее описание относится к восстановленному формату сбора.

Нативный модуль `iris_maxpatrol_module` получает инциденты MaxPatrol SIEM
и создаёт обычные оповещения IRIS через `alerts_create`: с обработчиками модулей,
уведомлением интерфейса и запуском правил. Отдельный bridge, API-ключ IRIS и
внешний процесс не нужны. Модуль изначально выключен.

## Подключение

1. Установить обновлённый backend в app и worker и применить миграцию
   до `utmn_maxpatrol03` штатным механизмом обновления IRIS. Для рабочего стека
   соблюдать `AGENTS.md`, включая резервную копию перед миграциями.
   Миграция следует за текущей `utmn_card_appendix4`; нельзя переносить её
   отдельно в другую цепочку миграций без проверки родительской ревизии.
2. Открыть **Настройки → Модули → MaxPatrol SIEM**. Если автоматическое
   добавление модулей отключено настройкой сервера, добавить модуль по имени
   `iris_maxpatrol_module` через существующую форму добавления.
3. Сохранить HTTPS-адрес SIEM и API-токен с правом чтения инцидентов/событий.
   Указать существующие ID клиента, критичности и статуса оповещения IRIS.
4. Включить модуль. Должны работать Celery worker и beat. Worker проверяет
   наступление срока опроса каждые 5 секунд; стандартный интервал — 30 секунд.

Первый опрос импортирует все доступные инциденты за последние 72 часа.
Новые связанные события дополняют сырое содержимое существующего оповещения;
дубликат оповещения не создаётся. Название, описание, статус и заметки аналитика
при таком дополнении не изменяются.
Задержка зависит от интервала, очереди worker и времени ответа SIEM;
push-подписки в предоставленном примере нет.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `siem_url` | пусто | HTTPS-адрес MaxPatrol SIEM |
| `api_token` | пусто | Bearer-токен SIEM |
| `customer_id` | `1` | Клиент IRIS, которому принадлежат оповещения |
| `interval` | `30` | Интервал опроса в секундах, 1–86400 |
| `lookback_hours` | `72` | Скользящее окно по времени создания, 1–8760 часов |
| `timeout` | `60` | Таймаут одного HTTP-запроса, 1–600 секунд |
| `severity_id` | `1` | Критичность оповещения IRIS, как в примере |
| `status_id` | `5` | Статус оповещения IRIS, как в примере |
| `verify_tls` | `true` | Проверять сертификат; `false` разрешает самоподписанный сертификат |

Токен шифруется существующим механизмом IRIS на основе `SECRET_KEY`.
В деталях модуля и экспорте конфигурации токен скрыт; сохранение пустого поля
не удаляет существующий токен. После смены `SECRET_KEY` токен нужно ввести заново.
При включённой проверке TLS внутренний CA следует установить в доверенное
хранилище образа app/worker. Перенаправления HTTP и неявные прокси из окружения
для этого клиента отключены.

## Логика и соответствие исходному примеру

- `POST /api/v2/incidents/`: тело запроса как в рабочем примере пользователя,
  страницы по 50, `timeFrom` из настроенного lookback, `timeTo=null`,
  `where=status != "Closed"`; сортировка `created descending`, `status ascending`,
  `severity descending`. Данные для оповещения берутся из строки этого списка.
- Отдельного GET карточки нет. Поля, отсутствующие в ответе списка, дополнительно
  не запрашиваются. Если описания нет, используется стандартное описание источника;
  критичность и статус IRIS задаются настройками модуля.
- `POST /api/events/v3/events/` с `incidentId`: связанные события, страницы по 250,
  строковый PDQL `select(...) | sort(time desc)`. Токен представления из ответа
  передаётся на следующую страницу.
  Сохранены поля выборки из предоставленного `export_incidents.py`.
  Поля `_checkpoint`, `_meta`, `_presentation`, `_whitelisting` и дополнительные
  поля таксономии 28.0 включены в выборку. Перед записью в БД из `alert_source_content`
  рекурсивно удаляются ключи JSON-объектов со значением `null`. Значения `false`,
  `0`, пустые строки и контейнеры сохраняются; исходный строковый `body` не преобразуется.
  Позиции элементов массивов сохраняются, в том числе элементы `null` внутри массивов.
  Очистка применяется после слияния старых и новых материалов, поэтому старые
  `null`-поля также удаляются при очередном обновлении оповещения.
  Запросы к API, в частности обязательное по примеру `timeTo=null` в списке
  инцидентов, этой очисткой не изменяются. Массовое изменение старых записей
  отдельно от обычного обновления не выполняется.
- Оповещение содержит название, описание, ссылку, исходный ID и
  `alert_source_content` с инцидентом, событиями и деревом вложенных событий.
  Источник — `MaxPatrol SIEM`, тег — `siem`.
  Время события берётся из `created`; при отсутствии корректной даты — время опроса.
- Как в примере, ошибка получения событий не мешает созданию оповещения:
  оно поступит с пустым списком событий и отметкой неполноты. Повторный опрос
  попытается дополнить сырой лог без создания нового оповещения.
- Ошибка получения подробностей или записи оповещения оставляет инцидент
  для повторного опроса. Повторные попытки ограничены скользящим окном:
  после длительной недоступности увеличить `lookback_hours` для восстановления.

## Состояние и параллельные задачи

### Вложенные события MP10 28.0

Основной источник — полная выборка через `/api/events/v3/events/`: ответ может
сразу содержать и корреляционное событие, и все UUID из его `subevents`.
Дерево всегда строится непосредственно из ответа, без дополнительных
запросов нормализованных объектов или вложенных событий. Порядок строк не важен:
даже если дочерние события идут раньше родителя, дерево начинается с родителя.

Для сбора событий используется только предоставленный пользователем
`POST /api/events/v3/events/` с исходным PDQL-фильтром на 335 полей.
Все страницы получаются этим же запросом; затем связи между полученными
объектами строятся по UUID. Если дочернего UUID нет в ответе, он сохраняется
в `missing_uuids`, а `complete` становится `false`. Другие маршруты событий
и дополнительные способы поиска не вызываются.
Один UUID раскрывается один раз при построении дерева;
имя правила нормализации в поле `id` не используется как уникальный ID.
Основной v3-запрос использует конечный интервал: для текущих инцидентов — окно
опроса; для исторического инцидента — интервал вокруг его `created` шириной
`lookback_hours` в каждую сторону. Нижняя граница не подменяется Unix epoch 0.
Если нужные события старше выбранного интервала, увеличить `lookback_hours`.

В сыром содержимом оповещения сохраняются:

- `events`: нормализованные объекты всех полученных событий, включая вложенные.
  Поля `body` и `mime` сохраняются, если SIEM их вернул; XML/JSON в `body`
  не преобразуется и не подменяется текстовым описанием `text`.
- `event_tree`: вложенные узлы `{uuid, event, subevents}`; `event` содержит
  полный объект. Повторные узлы и циклы представлены как `{uuid, reference: true}`.
- `event_links`: полная карта UUID родителя → UUID дочерних событий.
- `event_collection`: версия формата, время сбора, количества, `complete`,
  `missing_uuids`, ошибки и `source=incident_events_v3`.

Сохраняются все полученные события. Глубина отображаемого дерева ограничена 64 уровнями;
глубокие узлы представлены ссылками, их данные и связи остаются в `events`
и `event_links`. Недоступные/удалённые из хранилища события отмечаются явно.

Старые оповещения модуля автоматически дополняются после обновления worker,
в том числе если инцидент уже вышел за `lookback_hours`: для этого используются
сохранённые отметки импорта. Неполные выгрузки повторяются при очередном опросе;
полные обновляются не чаще раза в 5 минут (или реже, если `interval` больше).
Уже полученные поля и связи сохраняются при неполной повторной выгрузке.
Удалённые оповещения повторно не создаются.

Эталон сетевого запроса — рабочий пример пользователя, а не методы стороннего SDK.
Ранее добавленные вспомогательные v2-методы событий удалены из модуля.
Исходный `body` сохраняется, если он есть в v3-ответе; отдельный `/raw` не вызывается.

После получения пользователем реального ответа v3 выполнена локальная проверка:
12 событий, один родитель с 11 дочерними UUID, 11 непустых `body`. Все исходные
заполненные поля сохранены, а `null`-ключи удаляются на границе записи в БД;
дерево построено без дополнительных HTTP-запросов.
Сам ответ с данными инфраструктуры не включён в тестовые фикстуры репозитория.

Запрос дополнительно сверён с рабочим примером Postman пользователя:
`Content-Type: application/json`, те же 335 полей в строковом PDQL,
`incidentId`, `offset`, `limit=250`, `noCount=true`, целочисленные `timeFrom`/`timeTo`.
Лишние поля `site_address`, `site_alias`, `site_name` из прежней выборки удалены.
В тестах зафиксирован только публичный список полей, без адреса установки,
токена и исходных событий. При одинаковых входных границах тело запроса совпадает
с рабочим примером; в автоматическом опросе время рассчитывается динамически.
Это исправление выявленных расхождений, а не доказанная причина HTTP 400:
для её подтверждения нужен ответ сервера именно на неуспешный запрос.

`maxpatrol_poll_state` хранит время последней попытки опроса источника.
`maxpatrol_receipt` хранит ID уже импортированных инцидентов.
Источник определяется нормализованным адресом SIEM и клиентом IRIS.
Смена токена, перезапуск, выключение/включение и переустановка модуля
не сбрасывают отметки импорта. Изменение адреса или клиента создаёт отдельный источник.
Удаление оповещения не вызывает его повторный импорт.

Оповещение и отметка импорта фиксируются одной транзакцией при первом commit
в `alerts_create`. Ошибка последующего hook не создаёт дубль при следующем опросе;
такая ошибка отдельно отмечается в журнале worker, уже записанное оповещение сохраняется.
Параллельные задачи одного источника исключаются advisory lock PostgreSQL,
который удерживается отдельным соединением до завершения опроса.
Отключение модуля или изменение конфигурации проверяется перед обработкой
и перед созданием каждого оповещения; уже выполняющийся HTTP-запрос завершится по таймауту.

Не переносить `processed_incidents.json` из старого bridge автоматически.
Одновременный запуск старого bridge и нового модуля может создавать дубли:
их отметки импорта независимы. Старый bridge нужно остановить перед включением модуля.

## Проверка без SIEM

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s v3\backend\tests -p 'test_maxpatrol*.py'
```

Тесты проверяют контракт запросов, TLS, пагинацию, ошибки, отключение,
разделение источников, транзакционность и сохранение отметок после повторного
открытия сессии/удаления оповещения. SQL-тесты используют SQLite и изолированные
замены границ приложения; они не доказывают работу PostgreSQL advisory lock,
настоящих Celery задач, UI или совместимость с конкретной версией MaxPatrol SIEM.

## Диагностика на уровне INFO

DEBUG не требуется. Логи находятся в stdout/stderr worker, отдельного файла модуля нет.
Уровень INFO обычно включает также сообщения WARNING и ERROR.
Каждый цикл имеет `poll`, каждая строка обработки инцидента — `incident`,
также выводится `module`. Контекст изолирован между задачами и сбрасывается
после обработки. Worker и его обработчики логов должны разрешать INFO
(например, запуск Celery с `--loglevel=INFO`).
Пример успешного цикла (числа приведены для иллюстрации):

```text
INFO MaxPatrol poll started: module=7 interval=30
INFO MaxPatrol collection started: customer=1 time_from=... time_to=...
INFO MaxPatrol incidents page received: offset=0 count=10
INFO MaxPatrol incident import started: incident='new-incident-id'
INFO MaxPatrol events page received: incident='new-incident-id' offset=0 count=3
INFO MaxPatrol incident details received: incident='new-incident-id' events=3
INFO MaxPatrol incident imported: incident='new-incident-id'
INFO MaxPatrol collection summary: received=10 created=1 already_imported=9 failed=0 invalid=0 events_failed=0 complete=True
INFO MaxPatrol poll completed: module=7 alerts_created=1
```

- `incidents page received ... count=0` и `complete=True`: SIEM ответил корректным пустым списком.
- `received`: число инцидентов, просмотренных коллектором; `created`: записанные оповещения.
- `already_imported`: пропущены по сохранённым отметкам; это не ошибка.
- `failed`: ошибки импорта; `invalid`: записи без корректного ID.
- `events_failed`: не удалось получить события, импорт мог продолжиться без них.
- `refreshed`: число существующих оповещений, в которых обновлены связанные события.
- `incomplete_incidents`: число обработанных инцидентов с неполной выгрузкой событий.
- `duration_ms`: длительность запроса или цикла в миллисекундах.
- `complete=True` означает, что обход списка завершился; при этом нужно проверять `failed` и `events_failed`.
- `complete=False`: обход был прерван ошибкой, отключением модуля или изменением настроек.
  После ошибки списка итог может быть нулевым: это не подтверждает отсутствие инцидентов в SIEM.

При ошибке worker выводит `MaxPatrol poll failed: module=… stage=… reason=…`.
`stage=configuration` — разбор настроек, `source_lock` — блокировка источника,
`poll_state` — чтение/запись состояния в БД, `collection` — запросы и импорт.
Коды `reason`: `http_401`/`http_403` — отказ авторизации/доступа,
`tls_error` — ошибка TLS, `timeout` — превышен таймаут,
`connection_error` — ошибка соединения (в том числе DNS), `invalid_json` — некорректный JSON.
Для прочих ошибок выводится тип исключения без его содержимого.

Чтобы увидеть историю и продолжать просмотр в PowerShell из корня репозитория:

```powershell
docker compose -p iris-upgrade-2-4-29-fastapi -f docker-compose.upgrade-validation.yml -f docker-compose.saved-data.yml -f docker-compose.v3.yml -f docker-compose.v3-live.yml logs --tail 300 -f worker | Select-String -Pattern 'maxpatrol'
```

Эти сообщения появятся после установки обновлённых исходников в worker.
Токен, HTTP-заголовки, полные тела ответов и содержимое событий в логи не выводятся;
ID инцидентов выводятся в экранированном виде для сопоставления с SIEM.

При раскрытии вложенности на INFO видны `MaxPatrol HTTP completed` с методом,
endpoint, HTTP-статусом, длительностью и числом строк ответа, а также
`MaxPatrol subevents summary: roots=… events=… missing=… errors=… complete=…`.
Детальные `HTTP started` и `subevents page received` относятся к DEBUG;
для диагностики HTTP 400/500 включать DEBUG не требуется.
Успешный импорт оповещения не означает полную выгрузку: проверяйте также
`event_collection.complete` в его сыром содержимом.

Перед основным запросом INFO показывает `MaxPatrol events request: api=v3`
с `time_from`, `time_to`, `offset` и количеством полей. При неуспешном HTTP-ответе
WARNING содержит метод, endpoint и статус: это позволяет отличить отказ
запроса событий `/v3/events/` от ошибки списка `/api/v2/incidents/`.
В `MaxPatrol HTTP request failed` на WARNING теперь сразу виден ограниченный
очищенный фрагмент пояснения сервера в `response`, а также `status`, `reason`,
`duration_ms`, контекст цикла/инцидента и параметры времени, если они есть.
Заголовок Authorization и полное тело ответа в журнал не включаются.

При HTTP-ошибке в `event_collection.errors` сырого содержимого сохраняется
ограниченная диагностика: `reason`, `request_revision`, `method`, `endpoint`,
`time_from`, `time_to`, `fields_count`, `filter_sha256` и `response_excerpt`.
Фрагмент ответа ограничен 1024 символами; настроенный токен, Bearer-значения
и PAT-строки удаляются до обрезки. HTTP-заголовки в эту структуру не попадают.
Это позволяет установить причину HTTP 400 по объяснению SIEM вместо одного статуса.

`event_collection.version=2` — версия формата материалов IRIS, а не номер API SIEM.
Для определения версии выполняемого кода используется `request_revision`;
после установки обновления ожидается `mp10-inline-clean-json-3`.
Ранее сохранённый объект ошибки не изменится до следующего опроса и обновления
материалов существующего оповещения. Наличие только `reason=http_400` в старой
записи само по себе не определяет ни endpoint, ни версию работающего worker.

Используются только два рабочих POST-запроса пользователя: список инцидентов
и события инцидента. Прежний GET карточки удалён; отказ этого маршрута
больше не блокирует новые импорты. В сыром содержимом `incident_source=incidents_list_v2`
указывает источник данных. При обновлении имеющегося оповещения поля из новой
строки списка заменяют соответствующие сохранённые поля, а дополнительные
данные, собранные ранее, сохраняются. Для обновления старого оповещения вне
окна списка используется сохранённый объект (`incident_source=saved_import`).
Поля аналитика в самом оповещении не изменяются. Старое `incident_refresh_error`
сбрасывается после успешного обновления материалов.

### TLS и standalone-контейнер

При явно выбранном `verify_tls=false` модуль пишет одну строку
`MaxPatrol TLS certificate verification disabled: verify_tls=false` за клиент
(в worker — за цикл опроса). Повторяющиеся многострочные `InsecureRequestWarning`
urllib3 подавляются только для HTTP-вызова к настроенному хосту и только для
этой категории предупреждений. Проверка TLS не меняется, при `verify_tls=true`
фильтр не применяется. Постоянное глобальное отключение warnings не используется.
Область предупреждений рассчитана на синхронную Celery-задачу в prefork worker.

Пример нового формата (иллюстрация):

```text
INFO [module=7 poll="a1b2c3" incident="incident-id"] MaxPatrol HTTP completed: method=POST endpoint=/api/events/v3/events/ status=200 duration_ms=120.4 rows=12
INFO [module=7 poll="a1b2c3" incident="incident-id"] MaxPatrol incident events refreshed: incident='incident-id' events=12 complete=True missing=0 errors=0
WARNING [module=7 poll="a1b2c3" incident="incident-id"] MaxPatrol HTTP request failed: method=POST endpoint=/api/events/v3/events/ status=400 reason=http_400 duration_ms=52.1 response='Пояснение сервера'
```

Для standalone-контейнера Linux замените `IRIS_CONTAINER` на его имя:

```bash
docker logs --since 15m --timestamps -f IRIS_CONTAINER 2>&1 | grep --line-buffered -F 'MaxPatrol'
```

Для одного инцидента можно дополнительно отфильтровать контекст:

```bash
docker logs --since 15m --timestamps -f IRIS_CONTAINER 2>&1 | grep --line-buffered -F 'incident="UUID_ИНЦИДЕНТА"'
```

Изменения вступают в силу после обновления образа и перезапуска worker;
старые строки в `docker logs` не переписываются.
