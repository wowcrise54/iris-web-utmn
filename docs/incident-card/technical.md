# Хранение и API карточки

## Структура

Frontend — SvelteKit (`v3/frontend`), backend — native FastAPI с существующим
слоем REST Blueprint (`v3/backend`). Карточка не записывается в описание
кейса и не заменяет его произвольные атрибуты.

Таблица `incident_cards`: первичный ключ `case_id` одновременно является
внешним ключом `cases.case_id`, `ON DELETE CASCADE`; `fields` и `selections`
хранятся в JSONB. Дополнительно: `schema_version`, `revision`, `author_id`,
`author_name`, `created_at`, `updated_at`, `missing_sources`.
Автор и даты назначаются сервером. Каталог полей и опций находится в
`app/business/incident_card_catalog.py`, проверка и расчёты — в
`app/business/incident_cards.py`.

## API

Все ответы используют обычный JSON envelope IRIS. Чтение и выгрузка требуют
доступа к кейсу на чтение; изменение — полного доступа. Выбор источника дополнительно
проверяется относительно этого кейса. Неавторизованные запросы не получают данные карточки.

| Метод и путь | Поведение |
|---|---|
| `GET /api/v2/cases/{id}/incident-card` | Разрешённый снимок, каталог, источники и полнота; не создаёт запись |
| `PUT /api/v2/cases/{id}/incident-card` | Первое или последующее сохранение с ожидаемой ревизией |
| `GET /api/v2/cases/{id}/incident-card/export?timezone=Asia%2FYekaterinburg` | DOCX Base64 и печатный HTML из одного снимка |

Основные поля снимка: `schema_version`, `revision`, `meta`, `fields`,
`selections`, `derived`, `catalog`, `sources`, `warnings`, `completeness`.
Значение `fields[key]` содержит `value`, `mode` (`auto` / `manual`),
`source` и `status` (`ok` / `missing` / `manual`).

В `PUT` разрешены только `schema_version`, `revision`, `fields` и `selections`.
В каждой записи поля разрешены только `value` и `mode`. Источник,
вычисленные значения и авторство клиент не назначает.

```json
{
  "schema_version": 1,
  "revision": 0,
  "fields": {
    "description": {"value": "Фишинговое письмо", "mode": "manual"},
    "categories": {"value": [2], "mode": "manual"},
    "prioritization_type": {"value": "target", "mode": "manual"}
  },
  "selections": {"alert_id": 1}
}
```

`revision=0` означает ещё не сохранённую карточку. Сервер блокирует строку
родительского кейса, проверяет ревизию и увеличивает её на единицу. Это также
защищает от двух одновременных первых сохранений. Несовпадение даёт `409`.
Ошибки схемы, типов, дат и выбора чужих источников дают `400`; слишком большой
запрос — `413`. Максимальный размер запроса — 256 000 байт; ограничения
длины текста и списков проверяются сервером.

## Источники

| Группа | Правило |
|---|---|
| ID, название, описание, организация, критичность | Текущий кейс |
| Источник обнаружения, внешний ID, время события | Только явно выбранный связанный алёрт того же клиента |
| Затронутые активы, источник и цель | Явно выбранные активы кейса; роли не угадываются |
| Хеши | Выбранные IOC подходящего типа хеша |
| Файлы | Выбранные записи DataStore того же кейса |
| Действия | Выбранные задачи; статус должен соответствовать выполненным/планируемым |
| Контакты, последствия, типы, меры, участники, MITRE, учётная запись | Ручной ввод |
| Важность, приоритет, длительности | Расчёт; формулы в пользовательской инструкции |

Ручной режим сохраняется при обновлении источников. Недоступный автоматический
источник сохраняет предыдущий серверный снимок и его происхождение с предупреждением.
Служебные значения `source` и `status` никогда не принимаются из тела `PUT`.

## Экспорт и перенос кейса

В обычный JSON-экспорт кейса добавлено поле `incident_card`. В архиве переноса
добавлена сущность `incident_card`, последняя в списке зависимостей.
Перед экспортом автоматические значения разрешаются заново.
Ссылки выбора преобразуются в типизированные `asset:ID`, `ioc:ID`,
`dsfile:ID`, `task:ID`, затем сопоставляются с новыми ID при импорте.
Исходные числовые ID не используются как ID целевой базы.

Алёрты не входят в существующий архив переноса кейса, поэтому связь с исходным
алёртом разрывается явно. Его значения сохраняются как снимок, а карточка
показывает предупреждение до нового явного выбора источника. То же правило
действует для других объектов, отсутствующих в переносе.

## Миграция и обновление

Миграция `utmn_incident_card01` продолжает `d2a6b8c1e374` и только добавляет
таблицу. Она не создаёт карточки для всех старых кейсов и не изменяет их поля.

По прямому уточнению пользователя применять **только** Compose-проект
`iris-v3-validation-20261010`. Проверенные labels его контейнеров указывают
на `docker-compose.v3.yml`; адрес — `https://localhost:18545`, backend —
`http://127.0.0.1:18084`. Его external-тома имеют префикс
`iris-v3-validation-20261010`. Конфигурация `v3-live` относится к другому
набору томов и в этом обновлении не используется.

Перед миграцией проверить labels и тома, записи и файлы; сделать `pg_dump -Fc`,
скопировать его на хост и проверить `pg_restore --list`. Дамп БД не содержит
файлов из отдельных томов. Томам не менять имена и подключения.
В командах явно задавать `-p iris-v3-validation-20261010 -f docker-compose.v3.yml`.
Обновлять app, worker и frontend; db/rabbitmq не пересоздавать.
После обновления проверить фактическую ревизию Alembic, сохранность записей и
хешей файлов, API, frontend и Celery worker.
